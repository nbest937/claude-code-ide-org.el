At any given level of the task tree — top-level headings, and
independently among each heading's own direct children — at most one
heading should ever be =NEXT= at a time, mirroring GTD's single "next
action" idea: two new =org-trigger-hook= functions (alongside the

39b08ecd-6350-48a2-b169-98535b626ac7) demote a superseded =NEXT=
sibling back to =TODO=, and auto-promote a sole surviving =TODO= in a
sibling group of two or more. See the plan for the full design,
including the resolved double-NEXT race and the two decisions made
during planning: a lone heading with no siblings is never
auto-promoted, and automatic transitions log identically to a manual
one plus an explanatory note.

Raised in conversation 2026-08-04, following the finding that Claude
Code has no dedicated Plan Mode enter/exit hook — only =PreToolUse=/
=PostToolUse= matched on the =ExitPlanMode= tool call, and nothing
fires on *entering* plan mode since that transition isn't a tool call
at all.

=PLANNING= slots between =NEXT= and =DOING=. Entry is a model
judgment call made *before* calling =EnterPlanMode= (Plan Mode itself
forbids non-readonly tool calls, so =org_set_todo= cannot run once
inside it — confirmed empirically during planning). Exit is
automatic: a =PostToolUse= hook matched on =ExitPlanMode= promotes
=PLANNING= → =DOING= in place, reusing the same continuous clock
interval rather than closing and reopening it. A "plan and implement"
prompt still produces both transitions at their correct, separate
times, never a premature jump to =DOING=.

Plan approved 2026-08-04, resolving the three original open
questions: =PLANNING= opens a clock exactly like =DOING= (no
=:LOGBOOK:= distinction between planning and implementation time);
the existing =claude-code-ide-org--trigger-auto-clock-in= trigger
hook gets a one-line =member= check extended to =PLANNING=, no new
hook needed; and no session→heading mapping is required at all —
because only one clock can run globally and =PLANNING= is only ever
set by the model on its own heading, "promote whichever heading
currently owns the clock marker, iff its state is exactly PLANNING"
is sufficient, mirroring
=claude-code-ide-org--blocker-clock-running-p='s existing
clock-marker-identity pattern.

One new gap surfaced *during* planning itself, not anticipated up
front: there's no reliable plan-approval/rejection signal available
to gate the promotion on. Confirmed empirically, not just assumed —
attempting to instrument a temporary capture hook to inspect a live
=ExitPlanMode= payload is itself a non-readonly action, which
re-triggers Plan Mode before the capture can run, which then blocks
the very instrumentation needed to capture it: circular by
construction. Accepted as a documented gap (same register as the
concurrent-session clock entry's "self-corrects" tolerance above) —
a stray promotion after a rejected plan is low-cost and self-corrects
the next time the heading's real state is set explicitly. See the
plan link for the full design and file-by-file implementation
breakdown.

Captured 2026-08-05 from conversation: how to kick off planning for
every open NEXT/TODO heading in parallel, while getting the resulting
=:SESSIONS:= bookkeeping right, given the constraint (confirmed live,
repeatedly, this same day) that org's clock is a single global
resource shared across every session touching this file.

*Core rule, structural not just cautious*: background planning agents
never transition any heading's TODO keyword and never call
=org_clock_in=/=org_set_todo=-to-=PLANNING=. Both
=claude-code-ide-org--planning-owner-session-id= and
=claude-code-ide-org--clock-owner-session-id= are single global
variables, and =claude-code-ide-org--promote-planning-to-doing=
promotes "whichever heading currently owns the running clock" — so N
simultaneous =PLANNING= owners is structurally impossible, not merely
awkward. There is exactly one clock. Background agents do read-only
research and write only their own plan file
(=~/.claude/plans/<slug>.md=); nothing about that touches the shared
clock, so it is the only part of this safe to genuinely parallelize.

*Write-back* (applying results to =TODO.org= — the Plan link plus a
session-bracketing =:SESSIONS:= note per heading):
- Serialize it: one heading at a time, only after each agent reports
  done.
- Route every write through =emacsclient=/elisp, not a raw external
  file write, even for headings with no clock currently running on
  them — unconditional consistency, not a per-call "is it safe right
  now" check. Directly motivated by
  [[id:53b0047d-c55c-486c-8eed-ba4994d97a1a][Direct file writes to a live org buffer can desync org-clock-marker]].
- Use =claude-code-ide-org--log-session-event= for the synthetic
  =:SESSIONS:= entries rather than hand-writing text — keeps the
  format forward-compatible with
  [[id:2b0988ed-eb92-4fa7-904a-cb2d10941bfd][Reorder :SESSIONS: entries to match :LOGBOOK: ordering]]'s pending
  flip, and guarantees correct drawer-append semantics.
- Re-resolve each heading fresh by =:ID:= at write time
  (=claude-code-ide-org--at-id=, the pattern every existing tool
  already uses) rather than trusting any position cached from when
  the agent was launched — other sessions touch this file constantly,
  demonstrated repeatedly today, including while this very design was
  being written up.
- Tag the synthetic =:SESSIONS:= entry with a distinct synthetic
  identifier, never this orchestrating session's own real
  =session_id= — misattributing unattended background research time
  as this session's own interactive work would be exactly the kind of
  noise
  [[id:782cda6c-111c-454e-93eb-b2b27012078b][Audit for clock/session bookkeeping noise before committing during a clocking-suppressed session]]
  is worried about.
- No =:LOGBOOK:=/CLOCK entries at all, by design — the single-clock
  model cannot represent true parallelism honestly, so don't try.
- Don't auto-commit the resulting batch. Leave it for explicit
  review — finalizing an auto-commit policy here would mean guessing
  at exactly the still-open question in
  [[id:3cb3f955-f10a-47cd-84ab-e629d73ea59d][Org skill: commit a newly-captured TODO immediately, when safe]]
  and [[id:782cda6c-111c-454e-93eb-b2b27012078b][the sibling heading above]].

Motivated concretely, not hypothetically: while this design was being

[[file:~/.claude/plans/capture-commit-safety.md][Plan]]

Captured 2026-08-04 from conversation: right now, capturing a new org
heading (per CLAUDE.md's "any time a new task is described in
conversation, create an org heading" rule) only edits the working tree
— nothing commits it, so it sits as an uncommitted change alongside
whatever else is in progress until a human notices and commits by
hand. Tell the org skill to commit the capture itself, immediately,
*given that it's safe to do so*.

"Safe" needs pinning down during planning, but at minimum: only the
=.org= file(s) touched by the capture are staged (never a broad
=git add -A=/=git add .=, per this project's own general git-safety
practice), the repo isn't mid-rebase/mid-merge/otherwise in a weird
state, and — the tricky part — the capture commit doesn't get tangled
up with *other* unrelated uncommitted changes already sitting in the
same file from earlier in the session (a commit should be scoped to
the capture, not sweep up unrelated in-progress edits just because
they're in the same file). Whether that means a targeted
=git commit -- TODO.org= (commits the whole file's current diff,
including any unrelated hunks) is actually "safe" in the sense meant
here, or whether something narrower is needed, is exactly the kind of
question actual planning should resolve rather than deciding here.

Should this be prose guidance in the skill (the model decides "is this
one safe" case by case, same register as the existing read-only-buffer
guidance) or something more mechanical? Lean prose, given the "safe"
judgment call looks inherently contextual rather than a fixed
checklist — same reasoning CLAUDE.md already uses elsewhere for calls

*What the tradition says — both findings cut against having =DOING=:*
- The canonical org+GTD reference (Bernt Hansen, https://doc.norang.ca/org-mode.html)
  runs =TODO(t) NEXT(n) | DONE(d!)= plus =WAITING(w@/!) HOLD(h@/!) |
  CANCELLED(c@)=. No in-progress keyword at all: *clocking* signals what

- GTD proper treats an in-progress state as a smell. A next action is
  "the next physical, visible activity"; anything needing an
  in-progress marker is usually a project wearing an action's clothes,
  and the prescribed fix is decomposition, not another keyword.

*=DOING= survives that critique here, for the reason it usually fails
it.* The standard substitute — let the clock say what is active — is
exactly the affordance

already commits to clock accuracy being "only ever as fresh as the last

record cannot answer "what is being worked on right now," so the
keyword has to. Worth recording explicitly, because a future reader
citing Bernt or GTD would have a well-supported argument for deleting
=DOING= and would be wrong *for this system specifically*.

The user's own narrowing helps too: =DOING= means actively working on
implementation and testing — a named phase, not an open-ended
in-progress limbo, which is what GTD actually objects to.

=DONE=.* Headings here repeatedly sit in =DOING= carrying "*Still
owed:* an interactive by-hand pass" — implementation and tests

not =DOING=, and under this project's "verified, not just implemented"
bar it is certainly not =DONE=. The state is *structural*, not
incidental: verification is human-triggered by hard constraint (Claude

mandatory handoff that currently has no name and lives only as prose.
org's own manual uses exactly this slot in its example sequence,
=#+TODO: TODO FEEDBACK VERIFY | DONE CANCELED= (org-manual.org:4210).

and so was quietly suppressed for every tool-driven transition ever

logging model assumes one human, one buffer, one synchronous
keypress at a time. This project's actual workload — concurrent
sessions, background agents, non-interactive =emacsclient= calls, a
global clock paused/resumed across turn boundaries — is the opposite
of that, and every incident above traces back to the same mismatch.

version of this redesign would make most of =PLANNING='s current

*Proposed redesign:* Claude Code sessions stop touching the live
Emacs buffer for anything clock- or state-sensitive. Instead they
append plain, dumb, append-only JSON events to a per-session file
(e.g. =~/.claude/org-updates/<session_id>.jsonl=) — no buffer edits,
no clock mutation, no non-interactive logging trigger, most of it not
even requiring Emacs to be reachable to write. A new interactive
Emacs command reads the accumulated events across all pending session
files, presents them to the human as a reviewable batch (think
=org-agenda='s bulk-mark UI or =magit-status='s staging area, not a
raw diff), and applies the approved subset through org's *real*,
synchronous, single-actor machinery — =org-todo=, =org-clock-in=,
=org-clock-out= — called for real, inside a genuinely interactive
command, so native =!=/=@= logging finally just works instead of
needing to be suppressed.

*Not everything moves* — only the two categories that have actually
caused every incident: TODO-state transitions and clock start/stop.

| Stays direct, as today                                    | Moves to queue + review              |
|------------------------------------------------------------+---------------------------------------|
| =org_query= (read-only)                                    | =org_set_todo= (all states — needed for logging to fire, not just clock states) |
| =org_clock_report= (read-only)                              | =org_clock_in= / =org_clock_out=       |
| =org_refile=, =org_archive=, =org_move_sibling=, =org_sort_children= (never implicated in any incident) | Stop/UserPromptSubmit session-pause/resume signals (become bare timestamp appends — no Emacs call, no owner variable, no cross-session race, since there's no shared live clock left to race on) |
| =org_capture= (heading creation — separate, orthogonal bugs already noted elsewhere) | |
| =org_log_background_plan= (already deliberately clock/state-free — already exactly this pattern) | |

*What this eliminates* (mapped against the evidence above): marker
desync (no writer but the human-driven apply command ever touches
=TODO.org=/=DONE.org=), the idle-clock-hijack and missing-ownership
bugs (moot — ownership is just the queue filename, no shared clock to
inherit), the malformed-concurrent-write =CLOCK:= corruption (exactly
one writer, one operation at a time), the noise-vs-genuine bookkeeping
judgment call (reviewed *before* anything lands, with session/timing
visible, instead of reconstructed from a git diff after the fact —
[[id:782cda6c-111c-454e-93eb-b2b27012078b][Audit for clock/session
bookkeeping noise before committing during a clocking-suppressed

**Core design principle, added 2026-08-06 from conversation: two
genuinely different modes, not one uniform "propose an interval"
behavior** — the system cannot tell when a human was actually
reading/thinking/composing versus idle, attending to something else
entirely (another task, email, lunch), between logged interaction
points, so it must not pretend otherwise:
- **Unattended/subagent-derived events**
  ([[id:16160d23-273b-4510-858e-db18508d04a0][16160d23]]) — the
  interval genuinely *is* knowable (a subagent was either running or
  not; =duration_ms= is authoritative), so the apply command can
  propose, and the human can accept in bulk, a real =CLOCK:= entry
  directly. Still reviewed, per the core queue+review model — but
  mechanically derived, not reconstructed.
- **Human-session-derived events** — the apply command must *not*
  auto-write a =CLOCK:= interval on the human's behalf; doing so
  would be exactly the kind of "confidently wrong" record this whole
  redesign exists to avoid. Instead: render each logged =pause=/
  =resume= interaction timestamp
  ([[id:32272061-1d78-4726-b13b-90338edb2ba5][32272061]]) as an
  *active*-timestamp annotation line alongside the heading's =:LOGBOOK:=
  — a "guidepost," not a claim of attention — and leave the actual
  =CLOCK:= interval for the human to draw/type/adjust themselves. A
  suggested default (e.g. span from first to last guidepost in a
  tightly-clustered run) is fine to offer, but must be clearly
  editable/rejectable, never silently committed as fact.

timestamp convention captured the same day: an *active* annotation
(=<start>--<end> label=) means "a human was logged interacting with
this span, worth a glance in the agenda"; the =CLOCK:= line itself
stays *inactive* as org already does it, unchanged, still the sole
arithmetic source of truth. This lets org's own agenda double as a
free, retrospective "what did I actually attend to" view, no bespoke
code needed for that part — see
[[id:c084553c-0621-4a96-9fa1-f32850aeec6a][c084553c]] for the
verification step this leans on before being trusted.

*What happened:* the queue held a =todo → PLANNING= event stamped 11:51.
By the time it was applied, the heading had long since moved on to
=DOING= (promoted by =bin/hooks/exitplanmode-promote-planning=, which

*Why it is not just an =exitplanmode= problem:*
[[id:feba67eb-35b3-48bd-a892-8ecd47ca52e0][feba67eb]] already plans to
make that hook emit a queued =todo= event, which would have avoided this
particular instance. But the general hazard survives that fix — a queue
is reviewed at a moment of the human's choosing, possibly long after the
events were recorded, and *any* out-of-band change in between (a
hand-edit in Emacs, a different session, an org-agenda bulk action)
leaves the queued transition stale. The longer review is deferred, the
likelier this gets, and deferring review is the entire premise of the
design.

*Options, none settled:*
- *Verify before applying*: compare the event's implied "from" state
  against the heading's actual current state, and refuse — or flag in
  the review buffer — when they disagree. The queue does not currently
  record a "from" state, only a "to", so this needs a schema addition.
- *Show current state in the review buffer* next to the proposed one, so
  a human sees =DOING → PLANNING= and declines it themselves. Cheaper,
  and consistent with the design's "the human is the validation step"
  premise, but relies on them noticing.
- *Collapse per heading*: apply only the final queued state per heading
  rather than replaying each transition. Loses the intermediate log
  lines that [[file:~/.claude/plans/review-and-cutover.md][the plan]]
  deliberately wanted, and still regresses when reality moved past even
  the final one.

surfacing a mismatch in the review buffer — cheap, no new failure mode,
and it makes the human's decision an informed one rather than a
guess. Not started.

|             | is ever written              | on disk, nothing consumes them |
| recoverable | no                           | *yes, in principle*            |

data structure anticipates this case and the review layer simply
declines to use it.

review time — then apply it exactly like any other confirmed interval.

alternative recorded at
[[id:a1d63f52-4c07-4b9e-8f31-6d2b90c4e7a5][a1d63f52]]):
- It demands no discipline in the moment. Remembering to clock a bucket
  requires predicting that you are about to do meta-work, which is
  precisely when nobody is thinking about bookkeeping.
- It answers *about what*, not just *how much*. A bucket can total the
  meta-work but can never say which task you were circling.
- "Which task was that, actually?" is retrospective judgement a human
  can make and a machine cannot — the same premise the entire
  queue-and-review model rests on. Assigning at review time is that
  premise applied to attribution instead of to approval.

belong to no task — backlog-wide triage, review before any task exists.

the part that would not have survived contact with practice.

- What a human does with a span they *cannot* place. Dropping it loses

  ignore the buffer. Neither is obviously right.
- One session's nil-keyed group can hold several unrelated activities.
  The existing gap-threshold clustering splits them by time, which is a
  proxy for topic and will sometimes be wrong.
- Whether assignment should offer the same completion as =org-refile=,

Proposed by the user 2026-08-11 as the middle ground between treating a
drained queue file as a permanent record and treating it as a spool:
mark batches consumed, but *guarantee ingestion is idempotent*, so an
old file can be un-marked and reprocessed — after a logic change, a
corruption, or a bug found later. An archive folder rather than a flag
was suggested as the more attractive mechanism.

*The archive half already exists, by accident.* It was created
2026-08-10 to hold the stranded =d847eab1= file, and it needs no code at
all: =--queue-session-ids= calls =directory-files= non-recursively,
filtered to =\.jsonl\'=, so a subdirectory is already invisible to the
reader. That is exactly why an archive folder beats a consumed-flag —
the flag would need reader changes, and this is proven working. What is
missing is a command to move drained files there (today a manual =mv=)
and one to bring them back.

*The idempotent half is one third done, and was not framed as such.*
Apply has three write paths:
- *State transitions — already effectively idempotent,* via
  [[id:f9f61c04-150b-4ee7-96c9-582cf2bda95a][f9f61c04]]'s staleness
  guard. Replaying an applied transition means its =from= no longer
  matches the heading's current state, so it is flagged and refused.
  That guard was built to prevent regressing a heading; it turns out to
  be the first piece of idempotent ingestion.
- *=CLOCK:= intervals — not idempotent.* =--review-apply-clock= drives
  =org-clock-in=/=org-clock-out= with no check on what is already there,
  so a replay writes a duplicate interval and silently doubles the
  recorded time.
- *Annotations — not idempotent.* =--append-to-drawer= checks only that
  the *drawer* exists, never that the line does.

*Proposal: content-based idempotency, not bookkeeping.* Both remaining
cases are cheap because the output is deterministic from the event. An
interval with identical endpoints on the same heading is a duplicate,
not two real intervals a human happened to confirm twice; an annotation
line is a pure function of its span and label, so a string match
suffices. Checking the destination is strictly better than tracking
applied identities in a sidecar, because it survives losing the sidecar
— which is precisely the situation reprocessing an archived file puts
you in.

*Archive the =.applied= sidecar alongside its =.jsonl=.* Otherwise a
restored file loses the record of what was already applied, and
selective reprocessing becomes impossible. Note the two reprocessing
modes want different things: fixing a corruption wants the sidecar
honoured, while re-deriving under new logic wants it ignored so
everything is re-examined, with content-idempotency absorbing the
overlap. Support both, or pick one deliberately.

*Growth is not a real objection.* These are short JSONL lines; a year of
heavy use is a few megabytes. The reason to bound the live queue
directory is review-buffer legibility, not disk.

*This resolves* [[id:9d2fcdad-9bf7-47b6-8018-223b13ec4577][9d2fcdad]]:
once archived files are permanent by default and restorable, the raw
pause/resume history has a durable home, and the =:SESSIONS:= drawer has
no remaining job.

*The part that does not end at the cutover.* Post-cutover nothing moves
the file until apply moves it. So a batch holding a chain on one heading
(=TODO -> NEXT=, then =NEXT -> DOING=) records the same =from= on both

moves; the second then re-checks its =from= against a file that has

*Why that matters more than the noise itself.* A flag that fires on

  the earlier marked items in this batch will have left behind — rather

*The concrete argument for it, from this session's own data.* Of the

heading; they inherit whichever one the surrounding

is open are unattributable and silently dropped. Meta-work is precisely
when no clock is open. So today that time is not merely misattributed --
it is invisible, which is in direct tension with this project's second
stated goal of trustworthy tracking of where attention actually went.

A standing task, clocked during that work, gives those guideposts a
bracket to attach to. Nothing else has to change for it to work.

*Check org's own mechanism first, per
[[id:c084553c-0621-4a96-9fa1-f32850aeec6a][c084553c]].* Org already has
a name for this concept: =org-clock-default-task=, set with
=org-clock-mark-default-task=, a designated fallback task you can clock

a parallel convention -- exactly the reflex c084553c exists to enforce.

  default, the record gets *less* informative, not more -- a large
  bucket labelled "misc" answers no question worth asking. Scope it to
  genuinely cross-cutting work, and treat the review pass as the place
  to re-attribute a span that turned out to be about one task.
- *It never reaches DONE.* A permanent open task sits in a sibling group
  alongside the single-NEXT-per-level triggers

  =--trigger-demote-conflicting-next=). Check how those behave with a
  sibling that is deliberately never finished before relying on it. It
  also never archives, so its =:LOGBOOK:= grows without bound -- probably

*This was never stated anywhere, though nothing forbade it.* CLAUDE.md's

task was I circling."

work that genuinely belongs to no single task — "what's next?" surveys

Raised by the user 2026-08-10. None of the MCP tools bind
=inhibit-read-only=, so any of them fails outright with a
=buffer-read-only= error against a buffer the user has toggled
read-only (=C-x C-q=). The standing workaround -- documented in
CLAUDE.md's "Read-only buffers" note -- is to clear the flag and
proceed without asking, since the user sets it to guard against their
own stray keystrokes, not to block Claude.

*The gap:* nothing ever restores it. Every clear silently disables that
guard from then on, and the user only finds out by noticing. The
workaround was written as a way past an error, and the other half was
never specified.

*Leading fix, not settled:* have the tool wrappers bind
=inhibit-read-only= t around their own writes, so the user's flag is
never touched at all. Strictly better than clear-then-restore, which
has a failure window (a tool erroring mid-call leaves the buffer
cleared) and races badly with concurrent sessions -- two of them
interleaving clear/restore can restore a flag the other still needs
cleared, or leave it cleared anyway. Binding has no window and no
shared state.

*The one thing it rested on is now verified.* Read-only guards
modification, not saving, so =save-buffer= ought to succeed under
=inhibit-read-only= -- but every tool here saves, and an unverified
"ought to" in the save path is how this project has acquired bugs
before. Confirmed in passing 2026-08-10: this very heading was inserted
into =TODO.org= while its buffer was read-only, using exactly the
proposed binding. The text reached disk, the buffer came back unmodified,
and =buffer-read-only= was still =t= afterwards. So the fix is a small
edit to each wrapper, not a research question.

Cheap and self-contained; no dependency on
[[id:b5f7c5c7-7ad6-4c68-9cce-3479db1f1644][b5f7c5c7]]. Note the
refactor does *not* make it moot: after the cutover the review-and-apply
command becomes the only writer of live state, and it writes to exactly
the buffers the user is most likely to be viewing read-only at the time.

Two documents encode the current half-answer and must be updated
together with the fix: CLAUDE.md's "Read-only buffers" paragraph under
the MCP tools table, and the =feedback-todo-org-read-only= memory.

*Raised in priority 2026-08-10 by the interactive apply hitting it.* The
first real =claude-code-ide-org-review= apply against a read-only
=TODO.org= failed outright; toggling =C-x C-q= and re-applying
succeeded. Two things make this a sharper case than the MCP-tool one
above, rather than another instance of it:

- *The gesture is the opposite of a stray keystroke.* Read-only exists to
  stop the buffer being edited by accident. =M-x
  claude-code-ide-org-review=, then =m=, then =x= is about as deliberate
  as an action gets, and it is the human's own hands doing it. The guard
  fires on precisely the case it was never meant to catch.
- *After the cutover this blocks the only writer there is.*
  [[id:feba67eb-35b3-48bd-a892-8ecd47ca52e0][feba67eb]] makes apply the
  sole path by which anything reaches an org file. A user who habitually
  keeps =TODO.org= read-only while reading it would then find the entire
  system silently unable to record anything, with a raw
  =buffer-read-only= error as the only clue.

So the wrapper fix above should cover
=claude-code-ide-org--review-apply-item= too, not just the MCP tools.

*One property confirmed by the failure, worth keeping:*
=--review-apply= records only items that returned no error, so the
failed attempt marked nothing applied and the retry was clean -- no
double-application, no half-applied batch. Whatever the fix, do not
regress that.

** TODO Jump to a heading by title, not by pasting a UUID :code:
:PROPERTIES:
:ID:       915378ac-3bd4-461d-b0f0-83f67fbb3dac
:CREATED:  [2026-08-11 Tue 12:02]
:END:

=org-id-goto= wants the *entire* ID, exactly, and offers no help getting
it. Verified against the installed org 2026-08-11: it is
=(interactive "sID: ")=, a plain string prompt with no =completing-read=;
=org-id-find= resolves through the =org-id-locations= hash, which is
exact by construction; and the file-level fallback calls
=org-find-entry-with-id=, also exact. A miss is worse than a fast
failure — =org-id-find= re-runs =org-id-update-id-locations= and tries
again, so a partial ID costs a full rescan before returning nothing.

*Why this bites here specifically.* This project is unusually
ID-centric: every heading carries an =:ID:=, headings cross-reference
each other as =[[id:...]]=, and both conversation and commit messages
routinely name headings by their first eight characters — =720b2dcf=,
=f9f61c04=. Those abbreviations are readable and completely
unactionable. The gap is not org's fault; it is the cost of a convention
this project adopted deliberately.

*Proposal:* an interactive command that =completing-read=s over the
known headings, displaying *titles* rather than UUIDs, and jumps via
=org-id-goto= with the full ID behind the candidate.

*One design detail worth getting right:* annotate each candidate with
the ID's first eight characters. Doom's completion styles match against
the whole candidate string, so typing =720b2dcf= would then narrow
directly — which makes every abbreviation in these headings, in commit
messages and in conversation immediately typeable, rather than
something to look up first. That is most of the value; titles alone
would be a lesser tool.

*Building the candidates:* =org-id-locations= maps id to file and knows
nothing about titles, so they have to come from a scan. Either =org-ql=
over =claude-code-ide-org--tracked-files= — already a dependency, and
the same path =org_query= uses — or a plain =org-map-entries=. Do not
cache without measuring first: the tracked set is two files and well
under a hundred headings, so a rescan per invocation is very likely
cheaper than any invalidation bug it would buy.

*Not a gap, a convenience.* =C-c C-o= on any =[[id:...]]= link already
works and needs no new code, because the links in the file carry full
IDs. Scope this accordingly — it is a small command, not a subsystem.

*Testing:* the candidate-building function is ordinary and testable
(given a file set, assert the expected id/title pairs). The completion
UI itself is the fuzzy part and should be a documented manual check,
per this project's own "reasonably feasible" rule rather than forced
into a deterministic test.
