*Why TODO.org is a special case, not a template for org.skill in
general:* org.skill normally applies to a user's .org files living in
arbitrary other projects/folders — files with no relationship to a
git repo whose code is simultaneously being changed by parallel
subagents. TODO.org here is unusual on two axes at once: (1) it's
this repo's own tracked source file, in the same repo as the code
the subagents are editing, and (2) it's edited through two different
channels — live-Emacs/emacsclient (state, clock, archive) and
git-tracked branch diffs (plan-checkbox text) — that don't normally
have to coexist for an arbitrary end-user org file.

*Where the discussion landed, tentatively, before deferring:* the
real risk this session wasn't "two subagents' diffs collide" (rare —
different headings, same shape as config.el's clean merges) — it was
that the coordinator (this session) batched all TODO.org/DONE.org
commits at the very end instead of committing incrementally per
task, the same cadence used for config.el. That left git's tracked
TODO.org frozen at its pre-session state for the whole session while
the live-Emacs-edited on-disk file kept drifting — a mismatch that
has nothing to do with how many subagents are running or what they
touch. Tentative fix direction: commit TODO.org per-task (not
batched); let a subagent check off its own heading's boxes/decisions
directly in its own worktree; rely on the already-enabled
global-auto-revert-mode to sync the live buffer after a merge before
archiving that heading.

*Open questions for the fresh session:* does this generalize past
this repo's own meta-bookkeeping file, or is it inherently special
enough that any resulting rule belongs only in this repo's own
CLAUDE.md, not in org.skill/org-dev.skill? Should the CLAUDE.md rule
added this session ("coordinator reconciles the plan post-hoc") be
revised in favor of "subagent reconciles its own heading, coordinator
just commits incrementally") ? What's the actual failure mode if
auto-revert doesn't fire before an archive call — does it need an
explicit revert-buffer check rather than an assumption?

:SESSIONS: currently inherits the same Stop/UserPromptSubmit hooks as
:LOGBOOK:, so every turn boundary writes a Paused/Resumed pair — fine

=/dfd <task>= ("done for the day").

**** Plan [/]
- [ ] Detach :SESSIONS: writes from the Stop/UserPromptSubmit hooks
  entirely — CLOCK keeps its current per-turn pause/resume behavior
  unchanged; :SESSIONS: stops being written there
- [ ] Design =/dfd <task>=: closes the day's :SESSIONS: entry (and

- [ ] Handle the DONE+tested+committed close as a standing instruction
  (same shape as the DOING-transition rule in CLAUDE.md), not a hook —
  "tested and committed" is a judgment call nothing mechanical can

*** MAYBE Remote MCP access :code:
Off-machine access to the tools server and IDE-companion. This
session already got a =claude= CLI running directly in a Warp pane
on the same machine to reach Emacs (HTTP tools server +
IDE-companion lockfile, no vterm required). The obvious next step
is the same thing from *off-machine* — phone, another computer, a
CI job — but that means opening those servers beyond localhost,
which is real attack surface: arbitrary elisp execution against
your Emacs, today gated only by "it's on localhost." Don't build
this without designing auth first — bearer token at minimum, ideally
scoped per tool.

**** Plan [/]
- [ ] Add a bearer-token check to
  =claude-code-ide-mcp-http-server--handle-post= (new defcustom,
  nil-by-default = off) that short-circuits to a 401 before the
  request body is even parsed
- [ ] Add a matching =authToken= field to the WebSocket IDE-companion's
  lockfile and validate it in =claude-code-ide-mcp--on-open= — today
  it blindly attaches any connecting socket by port match, no
  identity check at all
- [ ] Make the hardcoded ="127.0.0.1"= bind address in both servers a
  defcustom
- [ ] Thread the token through =.mcp.json='s headers map on the
  client side rather than the URL, which tends to leak into logs
- [ ] Keep both servers bound to =127.0.0.1= permanently regardless,
  and require a tunnel (Tailscale/WireGuard/SSH) for actual remote
  reachability, with the token as a second factor

*Risk:* every registered tool call is unsandboxed elisp execution in
your live Emacs — a bearer token alone adds no TLS, per-tool
scoping, or rate limiting. Don't just flip the host to 0.0.0.0 and
call it done.
