Captured 2026-08-04 from conversation: right now, capturing a new org
heading (per CLAUDE.md's "any time a new task is described in
conversation, create an org heading" rule) only edits the working tree
— nothing commits it, so it sits as an uncommitted change alongside
whatever else is in progress until a human notices and commits by
hand. Tell the org skill to commit the capture itself, immediately,
*given that it's safe to do so*.

"Safe" needs pinning down during planning, but at minimum: only the
=.org= file(s) touched by the capture are staged (never a broad
=git add -A=/=git add .=, per this project's own general git-safety
practice), the repo isn't mid-rebase/mid-merge/otherwise in a weird
state, and — the tricky part — the capture commit doesn't get tangled
up with *other* unrelated uncommitted changes already sitting in the
same file from earlier in the session (a commit should be scoped to
the capture, not sweep up unrelated in-progress edits just because
they're in the same file). Whether that means a targeted
=git commit -- TODO.org= (commits the whole file's current diff,
including any unrelated hunks) is actually "safe" in the sense meant
here, or whether something narrower is needed, is exactly the kind of
question actual planning should resolve rather than deciding here.

Should this be prose guidance in the skill (the model decides "is this
one safe" case by case, same register as the existing read-only-buffer
guidance) or something more mechanical? Lean prose, given the "safe"
judgment call looks inherently contextual rather than a fixed
checklist — same reasoning CLAUDE.md already uses elsewhere for calls
that "only the model can make."

*Scope widened 2026-08-10, and the heading retitled to match.* What
started as "is =PLANNING= pulling its weight" became a review of the
whole progression, after checking the sequence against org+GTD practice
on the web. The original question is a sub-case and is answered in part
below.

*Census of TODO.org the same day, which is the most useful input here:*

: 23 MAYBE   14 TODO   14 DONE   2 NEXT   2 DOING   1 CANCELLED
:  0 PLANNING   0 WAIT

Those 56 are the *keyworded* headings; the file holds 63, the
difference being the seven top-level category headings, which carry no
TODO keyword by convention.

*What the tradition says — both findings cut against having =DOING=:*
- The canonical org+GTD reference (Bernt Hansen, https://doc.norang.ca/org-mode.html)
  runs =TODO(t) NEXT(n) | DONE(d!)= plus =WAITING(w@/!) HOLD(h@/!) |
  CANCELLED(c@)=. No in-progress keyword at all: *clocking* signals what
  is active, and he goes as far as switching tasks *to* =NEXT= on
  clock-in. =NEXT= means "available to work on now."
- GTD proper treats an in-progress state as a smell. A next action is
  "the next physical, visible activity"; anything needing an
  in-progress marker is usually a project wearing an action's clothes,
  and the prescribed fix is decomposition, not another keyword.

*=DOING= survives that critique here, for the reason it usually fails
it.* The standard substitute — let the clock say what is active — is
exactly the affordance
[[id:b5f7c5c7-7ad6-4c68-9cce-3479db1f1644][b5f7c5c7]] removes. CLAUDE.md
already commits to clock accuracy being "only ever as fresh as the last
time a human ran the review pass, not live." A reviewed historical
record cannot answer "what is being worked on right now," so the
keyword has to. Worth recording explicitly, because a future reader
citing Bernt or GTD would have a well-supported argument for deleting
=DOING= and would be wrong *for this system specifically*.

The user's own narrowing helps too: =DOING= means actively working on
implementation and testing — a named phase, not an open-ended
in-progress limbo, which is what GTD actually objects to.

*Proposal 1, the substantive one: add =VERIFY= between =DOING= and
=DONE=.* Headings here repeatedly sit in =DOING= carrying "*Still
owed:* an interactive by-hand pass" — implementation and tests
complete, verification outstanding. Under the definition above that is
not =DOING=, and under this project's "verified, not just implemented"
bar it is certainly not =DONE=. The state is *structural*, not
incidental: verification is human-triggered by hard constraint (Claude
cannot run the interactive apply), so every such task passes through a
mandatory handoff that currently has no name and lives only as prose.
org's own manual uses exactly this slot in its example sequence,
=#+TODO: TODO FEEDBACK VERIFY | DONE CANCELED= (org-manual.org:4210).

The payoff is a real queue: =VERIFY= becomes "what is waiting on *me*
to confirm," which is a next-action list in the GTD sense and does not
exist today in any queryable form.

: #+TODO: TODO NEXT PLANNING DOING VERIFY WAIT MAYBE | DONE CANCELLED

Clock rule if adopted: =DOING= → =VERIFY= closes the clock, since Claude
has stopped; the human's verification time clocks against the same
heading, which the convention recorded at
[[id:a1d63f52-4c07-4b9e-8f31-6d2b90c4e7a5][a1d63f52]] already permits.

*Proposal 2: get =MAYBE= out of the default agenda without changing the
keyword.* At 23 of the file's 56 keyworded headings it is the largest —
a perfectly healthy Someday/Maybe list, except that sitting before the
=|= renders it actionable. GTD is emphatic that Someday/Maybe lives
outside the active system and is reviewed periodically. Bernt's answer
is to keep such states active but filter them from default agenda views;
moving =MAYBE= after the =|= would be semantically wrong, since these
are not finished.

*Proposal 3: narrow =WAIT= to "waiting on a person."* It has never
been used once. GTD separates *Waiting For* (delegated, needs follow-up)
from *blocked* (dependency), and dependencies here are already expressed
structurally via =:BLOCKER:=. The current gloss, "blocked or waiting on
someone," overlaps that — and a keyword nobody reaches for is usually
one whose meaning is unclear rather than one whose situation never
arises.

*Bearing on this heading's original question.* The tradition supports a
planning state on its merits: planning is first-class GTD activity (the
Natural Planning Model), and =PLANNING= is on that basis *better*
grounded than =DOING=. But that answers only half the complaint recorded
above. Whether the *machinery* earns its complexity — the
=ExitPlanMode=-driven auto-promotion, the single global
=--planning-owner-session-id=, the hand-reversions logged above — is a
separate question the tradition says nothing about, and it stays open.
Do not read "GTD likes planning states" as "keep the hook."

Still =MAYBE=, still deferred on the original terms. Nothing above is
adopted; the sequence is unchanged pending a decision.

*A second question arrived 2026-08-14, and it belongs here rather than in
a heading of its own: should the set gain a =REVIEW= keyword?*

It came out of a live problem. =WAIT= had quietly acquired a second
meaning — the resting state at the end of a Claude work increment,
meaning "the ball is in the human's court" — used twice on 2026-08-13
before anyone noticed it was a pattern (see
[[id:d1cf852a-696a-4195-a4a7-039439c1f4b7][d1cf852a]]). Asked whether
=TODO= would serve the same end and be more idiomatic, the answer turned
out to be neither: *the keyword field is one slot serving two actors with
different views of who owes what.* =WAIT= is coherent from the session's
side (I handed this to someone else and am blocked on them — which is
=WAITING='s canonical GTD meaning) and odd from the human's, who does not
wait on themselves. =TODO= is coherent from the human's side and discards
both "work has happened here" and "this is owed back to you".

=REVIEW= is the only candidate that reads correctly from *both* sides,
and it does three things a rename would not:

- *It de-overloads =WAIT=,* which goes back to meaning blocked on an
  external party — someone you may have to chase. Those two states call
  for opposite actions and are currently indistinguishable.
- *It is a stage, not a parking state.* =WAIT= and =MAYBE= are places
  work sits; =REVIEW= is a step work passes through, between =DOING= and
  =DONE=. That gives it a principled position in the sequence.
- *It makes the session-start report actionable.* That report already
  surfaces every =WAIT= heading; "3 awaiting your review" is a list to
  act on, "3 WAIT" is not, and the two could then be reported apart.

*The objection to weigh against it is vocabulary collision.* The project
would then carry three meanings of "review": the =:review:= tag (a kind
of work), =claude-code-ide-org-review= (the command that applies the
queue), and a state. "The review buffer shows a REVIEW item tagged
:review:" is a sentence someone would have to write. Either choose a
different word for the state or adopt the collision deliberately and say
so in CLAUDE.md.

*Why it lands here rather than in its own heading:* adding a keyword
while this heading asks whether an existing one earns its keep should be
one decision about the *set*, not two taken months apart. The same
argument recorded above — that the assessment wants accumulated real use
rather than spot impressions — applies to =REVIEW= unchanged.

** TODO Fall back to the queue when org_capture cannot reach Emacs :code:
:PROPERTIES:
:ID:       7fa68d5c-b6c0-43df-85c6-764b1d56511f
:CREATED:  [2026-08-11 Tue 07:31]

=org_capture= requires a live Emacs. When the server is unreachable the
call fails outright and the task exists only in the conversation, which
ends. Not hypothetical: on 2026-08-10 the Emacs server was down for the
first ten minutes or so of a session (=emacsclient= reporting "can't
find socket"), and any capture attempted then would simply have been
lost.

This is the one creation path that cannot use the property the event
queue exists for — durable, cheap, no Emacs required. Everything else a
session records survives an Emacs outage; the act of writing down a new
task does not.

*Proposal:* attempt the live capture; on failure, append a =capture=
event to the queue, and let apply create the heading.

*Three things this raises, none of them settled:*
- *It is the queue's first outbox use.* Every existing kind is a
  proposal about a heading that already exists; a =capture= event would
  bring one into being. That is a genuinely different contract, and the
  review buffer would need to render it as such.
- *The :ID: must be minted by the session, not at apply time.* An ID
  assigned on application is useless to the session that queued it — it
  could not link to the heading, block on it, or clock against it, which
  is exactly what =claude-code-ide-org-capture= returns its ID for
  today. Minting without Emacs is fine (=org-id-new= is a UUID), but it
  means an ID can be referenced before the heading it names exists.
- *Reconciliation.* If the live capture succeeded and only its reply was
  lost, applying the queued event would duplicate the heading. A
  session-minted ID gives apply a cheap idempotency key: if that :ID:
  already resolves, the event is already realised.

*The larger caveat, which bears on this and on
[[id:cdcc065c-628d-4350-b1ba-fcf686e9c4c1][cdcc065c]] both.* This tool creates a bare
=* TODO <title>= at top level in a single target file. It cannot place a
heading under a named parent, nor carry tags, a body, or any property
beyond the =:ID:= it generates. Consequently almost every heading in
this project is written by direct Elisp instead — four were created that
way on 2026-08-10 alone, none through the tool. So instrumenting or
repairing =org_capture= improves a path that is rarely taken, and the
prior question is whether the tool should become capable enough to be
worth using. Decide that first; it may reorder or absorb both headings.

*Considered and set aside:* queueing a =capture= event on *every*
capture, as an audit record carrying =session_id=/=agent_id= — which is

*Added to scope 2026-08-13: document the sibling-survey idiom, in the
org skill.* Pairs directly with the "it can silently demote" warning
above — that warning says a =NEXT= nomination may demote a sibling, but
never says how to find out *which* sibling before committing to it.

The idiom: **to survey a heading's siblings, call =org_outline= scoped
to the _parent's_ =:ID:=**, with =active_only= and a =max_depth=. One
call, one screen:

: org_outline scope=<parent id> active_only=true max_depth=3

*Why it needs writing down rather than being obvious.* Twice on
2026-08-13 this check was done with a hand-rolled Python scan of
=TODO.org= instead, by someone who had used =org_outline= correctly an
hour earlier. The tool's =scope= parameter already documents "an =:ID:=
to index only that subtree" — the capability was never missing, only the
reflex. That is exactly the pattern
[[id:c084553c-0621-4a96-9fa1-f32850aeec6a][c084553c]] exists to catch,
and it recurred *inside* a session that had already invoked the tool.

*The one real limitation to document alongside it, so the idiom is not
mistaken for a full answer:* =org_outline= navigates *down* only.
Scoped to a leaf it returns that leaf and its descendants, never its
ancestors — so the caller must already know the parent's =:ID:=. There
is no upward navigation from a child. Adding a =relation: siblings=
parameter was considered on 2026-08-13 and *rejected in favour of this
documentation*: a new parameter would only shorten an idiom that already
works, on a tool whose value is being cheap to call.

*A second reason the survey matters, beyond demotion.* Scanning the file
with =grep= reads what is *on disk*, which post-cutover is not the same
as what has been *decided* — queued transitions have not landed yet.
=org_outline= reports the applied state, so the difference between "I set
this to NEXT" and "this is NEXT" stays visible. The Python scan on
2026-08-13 silently reported =TODO= for a heading whose promotion was
sitting in the queue; the answer was right, but only by luck of what was
being asked.

*The buffer-side half of the same idiom, added 2026-08-13.* =org_outline=
is a thin wrapper: the work is done by org's own =org-map-entries=, with
=org-id-find= to resolve a scope and about ten lines of ours to format
each line. Everything it does is therefore available directly from an
org buffer, and *more* is — which resolves the upward-navigation
limitation recorded above rather than leaving it open.

Two things =org-map-entries= offers that the MCP tool does not expose:

1. *Positional scopes.* =tree= (the subtree at point), =region=,
   =file=, =agenda=, or an explicit file list. So the sibling survey has
   a buffer-side form that needs no parent =:ID:= at all:

   : (save-excursion (org-up-heading-safe)
   :   (org-map-entries #'org-get-heading "/NEXT" 'tree))

   That is exactly the "navigate up from a child" case the tool cannot
   do, available for free from point. It is the reason a
   =relation: siblings= parameter stays rejected: the capability is not
   missing, only ID-addressed access to it.

2. *org's full MATCH query syntax* — the =/NEXT= above, and tags/property
   queries generally. =org_outline= has no MATCH argument and filters
   after the fact with =active_only=, so anything more selective than
   "drop DONE and CANCELLED" is easier from a buffer than through the
   tool.

*Two caveats to write down with it, both quiet failures.*
=org-map-entries= respects narrowing, so a narrowed buffer silently maps
only the visible portion and reports a confidently short answer. And
with a *file list* scope it visits those files; =org_outline='s docstring
records that this was verified not to move point or mark buffers
modified, which is what makes it safe against files the user has open —
worth preserving in the rewrite rather than rediscovering.

*Proposed shape: extend =org_outline=, do not add a third tool.*

1. =scope= accepts an =:ID:= *prefix*, resolving it when unambiguous and

2. When =scope= resolves to a heading, that heading's front matter

*This one actually happened, deliberately, as a resilience test.* On
2026-08-12 two sessions ran against this same checkout. This session
wrote a heading to TODO.org, staged it with an explicit pathspec
(=git add -- TODO.org=), and went to commit. The commit failed with

than the mislabelling.

*The mechanism is the index, not the files.* Every convention this
project already has is about file contents — check for a modified
buffer, stage explicitly, never =git add -A=. None of them touch the
actual shared mutable state, which is =.git/index=: one per checkout,
not one per session. Worse, following the convention *increased* the
damage. Staging early loaded this session's work into the index
*before* the other session committed; a pathspec-less =git commit= then
picked it up automatically. Had this session not staged at all, its
work would have been left alone.

*Not covered by the existing worktree heading, and this is the load-
bearing part.*
[[id:2e09adb7-6e29-499c-a40e-98cd2b327cff][2e09adb7]] concludes that
worktrees handle the *code* side — "one checkout + branch per session,
no shared-file collisions" — and that only the org files need to stay a
single canonical copy in the main checkout. Read against this incident
those two halves collide: the file that got swept up *was* TODO.org,
which by that heading's own =:ID:=-uniqueness and clock-fragmentation
argument is exactly the file that *cannot* be partitioned into a
worktree. So a worktree session must still write and commit TODO.org
in the main checkout, through the main checkout's index, and hits this
identically. **Worktrees do not fix this scenario; they fix everything
around it.** That is new information for 2e09adb7, which assumed the
code side was the whole problem.

*Related but distinct:*
[[id:3cb3f955-f10a-47cd-84ab-e629d73ea59d][3cb3f955]] already asks
whether =git commit -- TODO.org= is "safe," but scoped to a *single*
session not sweeping up its own unrelated hunks in the same file. This
heading is the cross-session case: another session's *staged* work, in
any file. Same command, different failure. Worth answering together.

*One mitigation is already verified.* Tested 2026-08-12 in a scratch
repo: with =A.txt= staged, =git commit -- B.txt= commits B only, leaves
A staged, and does not commit A. So a pathspec-scoped commit is
genuinely safe for the *other* session's work. The catch is that it
constrains the wrong party — safety depends on the *committing* session
complying, and the session at risk has no way to enforce it.

*Caveat found while defining the hook below:* =git commit -- <paths>=
*fails on an untracked file* — =error: pathspec 'NEW.txt' did not match
any file(s) known to git=. A new file must be =git add=-ed first, and
only then can be committed by pathspec. So for brand-new content (a new
plan, a new script) the staging window this mitigation exists to avoid
is unavoidable, and exposure persists between the add and the commit.
The mitigation is complete only for already-tracked files — which is
where this incident happened, TODO.org being tracked.

*Options for something robust, none chosen:*
- *Convention only:* ban =git add= outright in favour of
  =git commit -- <paths>=, in CLAUDE.md and the org skill. Cheapest,
  verified to work, and binds only sessions that follow it. Given both
  sessions here are Claude Code reading the same CLAUDE.md, this is
  less hollow than it sounds — but it is guidance, not a mechanism, and
  the user asked for a mechanism.
- *A =pre-commit= hook* in =.githooks/=. Defined below — the only
  option here that is a mechanism rather than guidance, and cheaper
  than first assumed.
- *Route git writes through the event queue* of
  [[id:b5f7c5c7-7ad6-4c68-9cce-3479db1f1644][b5f7c5c7]]. That queue
  already carries =session_id=/=agent_id= and already exists to stop
  concurrent sessions from mutating shared state directly, with a human
  applying batches later. Commits are the same shape of problem. The
  heaviest option and the most consistent with where the project is
  already going.

*The =pre-commit= option, defined.* Measured 2026-08-12 in a scratch
repo with a hook that printed its own environment. =GIT_INDEX_FILE=
identifies which command form invoked the commit:

| Command                  | =GIT_INDEX_FILE=            | Sweeps a staged file? |
|--------------------------+-----------------------------+-----------------------|
| =git commit=             | =.git/index=                | yes                   |
| =git commit --amend=     | =.git/index=                | yes                   |
| =git commit -a=          | =.git/index.lock=           | yes                   |
| =git commit -- <paths>=  | =.git/next-index-<pid>.lock= | no                   |

The hook can read *both* views at once: what the commit will contain
(=git diff --cached=) and what the real index holds
(=GIT_INDEX_FILE=$(git rev-parse --git-dir)/index git diff --cached=).
In the pathspec case those differ exactly as they should — commit
=B.txt=, real index still =A.txt=. =CLAUDE_CODE_SESSION_ID= also
propagates into the hook, confirmed by printing it.

*Proposed rule:* refuse when the form is a whole-index one (basename of
=GIT_INDEX_FILE= is =index= or =index.lock=) *and* the real index is
non-empty; fire only when =CLAUDE_CODE_SESSION_ID= is set. That is the
sweep case and nothing else. =git commit -- <paths>= always passes;
=git commit -a= against an empty index passes, since no one's work is at
risk; a human committing from a plain terminal is never affected. The
message should name the staged paths and print the pathspec form to use
instead.

*This retires the "needs ownership tracking" objection*, which the
first version of this heading asserted and which is wrong: the command
*form* is a sufficient discriminator and the safe form is
self-identifying. Per-session ownership of staged paths would only be
needed for a more permissive rule ("allow the sweep if everything
staged is mine"), not worth building first. If it ever is, the
precedent for where such state lives is
=claude-code-ide-org-queue-directory= — per-session runtime files,
deliberately outside the repo.

*Known limitations, all of them accepted rather than solved:*
- =--amend= is *indistinguishable* from a plain pathspec-less commit —
  both report =.git/index= — so it gets refused too, absent an escape
  hatch such as an =ALLOW_SWEEP= environment variable.
- =--no-verify= bypasses the hook entirely. This makes the mistake loud
  rather than silent; it does not make it impossible, and it still
  constrains the committing party rather than protecting the session at
  risk.
- Merge/rebase/cherry-pick paths are *untested* — the scratch-repo run
  errored before reaching them, and they need checking before shipping.
- Opt-in per clone via =core.hooksPath=, inheriting the same setup
  caveat =pre-push= already has.

*Testing* would follow the existing =bin/*-test= pattern
(=sync-plans-test=, =queue-append-test=): a scratch repo, each of the
four command forms, asserting exit status and message.

*Blocked on this in practice:* the user has stated they will not run a
second concurrent session until a mechanism is in place, so this gates
concurrent work generally rather than being one more backlog item.
