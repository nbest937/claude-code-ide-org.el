*** MAYBE Remote MCP access :code:
Off-machine access to the tools server and IDE-companion. This
session already got a =claude= CLI running directly in a Warp pane
on the same machine to reach Emacs (HTTP tools server +
IDE-companion lockfile, no vterm required). The obvious next step
is the same thing from *off-machine* — phone, another computer, a
CI job — but that means opening those servers beyond localhost,
which is real attack surface: arbitrary elisp execution against
your Emacs, today gated only by "it's on localhost." Don't build
this without designing auth first — bearer token at minimum, ideally
scoped per tool.

*Risk:* every registered tool call is unsandboxed elisp execution in
your live Emacs — a bearer token alone adds no TLS, per-tool
scoping, or rate limiting. Don't just flip the host to 0.0.0.0 and
call it done.

than a public API. Short of a real upstream PR, even just
generalizing it (hardcoded project path → variable) and writing it
up would make it something worth handing to someone else.

*Open question:* the wrapped functions (=register-session=,

Surfaced 2026-07-31 while relocating the statusline script
(=bin/statusline.fish=) into the repo: every other script in
=bin/=/=bin/hooks/=/=.claude/hooks/= is bash (mostly no extension,
one =.sh=), but the statusline script is fish — the only fish
dependency anywhere in this project, and one =future users= (per the
README/=CLAUDE.md= discussion) can't assume is installed the way bash
can be. Named =.fish= explicitly specifically so this deviation is
visible from the file listing rather than buried in the shebang, but
that's a stopgap, not a resolution.

*Update 2026-07-31:* option 1 (pure Emacs) below now has a real case
study, not just a hypothetical — see the sibling heading above ("Case
study: apply \"maximum Emacs\" to the statusline script", ID
e202e93d-cfa7-4d0a-8721-8f06428bc1e4). The statusline's =jq=-based
model-name extraction moved into Elisp
(=claude-code-ide-org--statusline-model-name=), and the shell wrapper
became =bin/statusline.sh= — plain POSIX =sh=, no =jq=, no fish — since
once the logic moves out, there's nothing left in the wrapper that
needs a fancier shell. The fish-vs-bash framing above is now
historical for this one script specifically (it's =sh= now, not fish),
but the broader project-wide decision (which of the five options to
standardize on) is still open.

Needs an actual decision, not just noticing the inconsistency:
1. Pure Emacs, given Emacs is already a hard dependency for every
   script in this project (they all end in an =emacsclient -e= call
   regardless of which shell wraps it). Rather than the shell side
   parsing stdin JSON (via =jq= or Python) and interpolating specific
   fields into an elisp expression string, write stdin to a temp file
   and pass *that path* to =emacsclient -e=, letting Elisp read and
   parse the raw JSON itself (native =json-parse-string=, no external
   dependency) and do all the field-extraction, decision logic, *and*
   output formatting — mirroring the temp-file convention this project
   already uses in the opposite direction for output
   (=claude-code-ide-org-write-*-report=). The shell wrapper would
   shrink to an near-unconditional stub: write stdin to a temp file,
   call emacsclient with its path, cat/format whatever comes back.
   Beyond just cutting the jq/Python dependency, this would eliminate
   an entire class of bug this project has already had to work around
   once (see =bin/hooks/session-pause=/=session-resume='s =jq -R -s .=
   JSON-string-encoding, specifically to avoid unsafe shell-to-elisp
   string interpolation) — if the shell layer never interpolates a
   parsed field into an elisp expression at all, that whole hazard
   disappears by construction rather than being carefully avoided each
   time.
2. Python instead of shell for some or all of these. Every hook
   script that parses the Claude Code JSON payload currently shells
   out to =jq=; Python's stdlib =json= module does that natively, no
   external dependency, arguably clearer than =jq='s own query
   language for anyone unfamiliar with it. Tradeoff: gives up the
   one-liner brevity these scripts have today for more verbose (if
   more structured) code, and Python, while extremely common on
   macOS/Linux dev machines, is still one more runtime assumption on
   top of whatever shell gets picked for the scripts that stay
   shell — this wouldn't replace the bash/fish/sh decision below so
   much as sit alongside it (e.g. "simple wrapper: shell; anything
   parsing/branching on JSON: Python").
3. Broader: is bash itself the right universal baseline for "future
   users," or should everything target POSIX =sh= for maximum
   portability instead?
4. Decide fish is fine for this one script specifically (e.g. if it's
   meaningfully clearer/shorter in fish) and document *why* it's the
   one exception, so a future contributor doesn't "fix" it back to
   bash without understanding the tradeoff, or
5. Standardize on bash (matching every other script) and rewrite
   =bin/statusline.fish= to drop the fish dependency entirely.

Whatever's decided should also cover: should this be written down as
a project convention (e.g. in CLAUDE.md's "Repository layout" or a new
"Scripting conventions" note) so it doesn't have to be
re-litigated per script.
