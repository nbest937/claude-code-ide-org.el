future tool call, from violating it. These three items are one

*** MAYBE Remote MCP access :code:
Off-machine access to the tools server and IDE-companion. This
session already got a =claude= CLI running directly in a Warp pane
on the same machine to reach Emacs (HTTP tools server +
IDE-companion lockfile, no vterm required). The obvious next step
is the same thing from *off-machine* — phone, another computer, a
CI job — but that means opening those servers beyond localhost,
which is real attack surface: arbitrary elisp execution against
your Emacs, today gated only by "it's on localhost." Don't build
this without designing auth first — bearer token at minimum, ideally
scoped per tool.

*Risk:* every registered tool call is unsandboxed elisp execution in
your live Emacs — a bearer token alone adds no TLS, per-tool
scoping, or rate limiting. Don't just flip the host to 0.0.0.0 and
call it done.

than a public API. Short of a real upstream PR, even just

*Open question:* the wrapped functions (=register-session=,
