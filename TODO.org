[[file:~/.claude/plans/twinkling-meandering-graham.md][Plan]]

At any given level of the task tree — top-level headings, and
independently among each heading's own direct children — at most one
heading should ever be =NEXT= at a time, mirroring GTD's single "next
action" idea: two new =org-trigger-hook= functions (alongside the
existing pair from "Enforce the transition rules", ID
39b08ecd-6350-48a2-b169-98535b626ac7) demote a superseded =NEXT=
sibling back to =TODO=, and auto-promote a sole surviving =TODO= in a
sibling group of two or more. See the plan for the full design,
including the resolved double-NEXT race and the two decisions made
during planning: a lone heading with no siblings is never
auto-promoted, and automatic transitions log identically to a manual
one plus an explanatory note.

*Verified, not just implemented:* =claude-code-ide-org--map-siblings=
(new shared helper) walks a heading's same-level siblings via org's own
=org-get-next-sibling=/=org-get-previous-sibling=, which stop at the
enclosing parent's boundary on their own — no special-casing needed
for top-level headings. Two new =org-trigger-hook= functions,
=claude-code-ide-org--trigger-demote-conflicting-next= and
=claude-code-ide-org--trigger-auto-promote-sole-todo=, registered
alongside the existing pair. Both deliberately carry no re-entrancy
boolean guard (unlike =claude-code-ide-org--auto-clock-in-active=) —
correctness is structural instead: each only re-derives sibling state
fresh from the live buffer, never from the hook's =change-plist=, which
is exactly what prevents the double-=NEXT= race (naively re-promoting a
heading the demote function just demoted). 11 new regression tests
cover top-level and direct-children demotion, cross-subtree isolation,
promotion on a non-NEXT transition (e.g. a sibling going =DONE=),
leaving a non-=TODO= or a two-=TODO= survivor group alone, the
race case itself, a pre-existing-invalid-state collapse, enforcement
via a bare =org-todo= call (not just the wrapper), and the
group-of-one exclusion (confirmed against the user's explicit call:
auto-promotion requires >= 2 siblings). One pre-existing test
(=...blocker-hook-only-blocks-own-heading=) was swept and fixed — it
incidentally created a 2-heading TODO-survivor group the new promote
hook would otherwise have mutated, unrelated to what that test
actually checks; isolated via a local =let=-shadow of
=org-trigger-hook=, matching the existing isolation pattern already
used by =...set-todo-reports-blocked-transition=. =bin/test= passes
106/106. Also verified live against the running Doom Emacs (reload,
then two separate scratch-file checks): demoting a superseded =NEXT=
sibling correctly writes an "Auto-demoted" =:LOGBOOK:= note and leaves
the new =NEXT= alone; reducing a 2-=TODO= group to one survivor via a
=DONE= transition (not a =NEXT= transition) correctly auto-promotes
the survivor with an "Auto-promoted" note; neither case triggered an
interactive note prompt.

[[file:~/.claude/plans/quirky-petting-lobster.md][Plan]]

Raised in conversation 2026-08-04, following the finding that Claude
Code has no dedicated Plan Mode enter/exit hook — only =PreToolUse=/
=PostToolUse= matched on the =ExitPlanMode= tool call, and nothing
fires on *entering* plan mode since that transition isn't a tool call
at all.

=PLANNING= slots between =NEXT= and =DOING=. Entry is a model
judgment call made *before* calling =EnterPlanMode= (Plan Mode itself
forbids non-readonly tool calls, so =org_set_todo= cannot run once
inside it — confirmed empirically during planning). Exit is
automatic: a =PostToolUse= hook matched on =ExitPlanMode= promotes
=PLANNING= → =DOING= in place, reusing the same continuous clock
interval rather than closing and reopening it. A "plan and implement"
prompt still produces both transitions at their correct, separate
times, never a premature jump to =DOING=.

Plan approved 2026-08-04, resolving the three original open
questions: =PLANNING= opens a clock exactly like =DOING= (no
=:LOGBOOK:= distinction between planning and implementation time);
the existing =claude-code-ide-org--trigger-auto-clock-in= trigger
hook gets a one-line =member= check extended to =PLANNING=, no new
hook needed; and no session→heading mapping is required at all —
because only one clock can run globally and =PLANNING= is only ever
set by the model on its own heading, "promote whichever heading
currently owns the clock marker, iff its state is exactly PLANNING"
is sufficient, mirroring
=claude-code-ide-org--blocker-clock-running-p='s existing
clock-marker-identity pattern.

One new gap surfaced *during* planning itself, not anticipated up
front: there's no reliable plan-approval/rejection signal available
to gate the promotion on. Confirmed empirically, not just assumed —
attempting to instrument a temporary capture hook to inspect a live
=ExitPlanMode= payload is itself a non-readonly action, which
re-triggers Plan Mode before the capture can run, which then blocks
the very instrumentation needed to capture it: circular by
construction. Accepted as a documented gap (same register as the
concurrent-session clock entry's "self-corrects" tolerance above) —
a stray promotion after a rejected plan is low-cost and self-corrects
the next time the heading's real state is set explicitly. See the
plan link for the full design and file-by-file implementation
breakdown.

Raised in conversation 2026-08-04: can separate Claude Code sessions
work on distinct TODOs simultaneously by each operating in its own
=git worktree= of a project repo? For the *code* side, yes — that's
exactly what worktrees are for, one checkout + branch per session,
no shared-file collisions. Emacs' own uniquify already disambiguates
same-basename buffers at different paths, so that part isn't even in
question.

Where it doesn't extend: =TODO.org=/=DONE.org= themselves must stay a
single canonical copy in the main checkout, not one copy per
worktree. Two failure modes rule out a per-worktree copy: (1) =:ID:=
lookups go through =org-id-locations=, a single global hash table
keyed by ID — a heading =:ID:= duplicated across two on-disk copies
(which a worktree checkout produces automatically) means whichever
copy was scanned last silently wins, with every =org_*= tool
targeting an unpredictable copy; (2) CLOCK/=:SESSIONS:= data written
into a worktree-local copy is invisible to =org_clock_report=/
=org_query=/the agenda until that branch merges, and is lost outright
if the worktree is torn down first — fragmenting exactly the
attention-tracking data the clock exists to keep whole. The single
clock living in one Emacs process reading one canonical file is the
mechanism that enforces "one attention at a time," not a limitation
to route around.

Related: [[id:337f7fb2-b9e9-4c02-82dd-d88e60df364b][Concurrent Claude Code sessions share one global org-clock with no session identity]]
already solved the narrower "which session owns the running clock"
problem this would otherwise collide with. This entry is scoped to
whether/how to formalize worktrees-for-code as a documented pattern

existing single-canonical-file constraint — not yet decided as worth
building anything for; may just be a documentation note rather than
code.

** MAYBE Remote MCP access :code:
Off-machine access to the tools server and IDE-companion. This
session already got a =claude= CLI running directly in a Warp pane
on the same machine to reach Emacs (HTTP tools server +
IDE-companion lockfile, no vterm required). The obvious next step
is the same thing from *off-machine* — phone, another computer, a
CI job — but that means opening those servers beyond localhost,
which is real attack surface: arbitrary elisp execution against
your Emacs, today gated only by "it's on localhost." Don't build
this without designing auth first — bearer token at minimum, ideally
scoped per tool.

*Risk:* every registered tool call is unsandboxed elisp execution in
your live Emacs — a bearer token alone adds no TLS, per-tool

(=bin/statusline.fish=) into the repo: every other script in

*Update 2026-07-31:* option 1 (pure Emacs) below now has a real case
study, not just a hypothetical — see the sibling heading above ("Case
study: apply \"maximum Emacs\" to the statusline script", ID
e202e93d-cfa7-4d0a-8721-8f06428bc1e4). The statusline's =jq=-based
model-name extraction moved into Elisp
(=claude-code-ide-org--statusline-model-name=), and the shell wrapper
became =bin/statusline.sh= — plain POSIX =sh=, no =jq=, no fish — since
once the logic moves out, there's nothing left in the wrapper that
needs a fancier shell. The fish-vs-bash framing above is now
historical for this one script specifically (it's =sh= now, not fish),
but the broader project-wide decision (which of the five options to
standardize on) is still open.

Needs an actual decision, not just noticing the inconsistency:
1. Pure Emacs, given Emacs is already a hard dependency for every
   script in this project (they all end in an =emacsclient -e= call
   regardless of which shell wraps it). Rather than the shell side
   parsing stdin JSON (via =jq= or Python) and interpolating specific
   fields into an elisp expression string, write stdin to a temp file
   and pass *that path* to =emacsclient -e=, letting Elisp read and
   parse the raw JSON itself (native =json-parse-string=, no external
   dependency) and do all the field-extraction, decision logic, *and*
   output formatting — mirroring the temp-file convention this project
   already uses in the opposite direction for output
   (=claude-code-ide-org-write-*-report=). The shell wrapper would
   shrink to an near-unconditional stub: write stdin to a temp file,
   call emacsclient with its path, cat/format whatever comes back.
   Beyond just cutting the jq/Python dependency, this would eliminate
   an entire class of bug this project has already had to work around
   once (see =bin/hooks/session-pause=/=session-resume='s =jq -R -s .=
   JSON-string-encoding, specifically to avoid unsafe shell-to-elisp
   string interpolation) — if the shell layer never interpolates a
   parsed field into an elisp expression at all, that whole hazard
   disappears by construction rather than being carefully avoided each
   time.
2. Python instead of shell for some or all of these. Every hook
   script that parses the Claude Code JSON payload currently shells
   out to =jq=; Python's stdlib =json= module does that natively, no
   external dependency, arguably clearer than =jq='s own query
   language for anyone unfamiliar with it. Tradeoff: gives up the
   one-liner brevity these scripts have today for more verbose (if
   more structured) code, and Python, while extremely common on
   macOS/Linux dev machines, is still one more runtime assumption on
   top of whatever shell gets picked for the scripts that stay
   shell — this wouldn't replace the bash/fish/sh decision below so
   much as sit alongside it (e.g. "simple wrapper: shell; anything
   parsing/branching on JSON: Python").
3. Broader: is bash itself the right universal baseline for "future
   users," or should everything target POSIX =sh= for maximum
   portability instead?
4. Decide fish is fine for this one script specifically (e.g. if it's
   meaningfully clearer/shorter in fish) and document *why* it's the
   one exception, so a future contributor doesn't "fix" it back to
   bash without understanding the tradeoff, or
5. Standardize on bash (matching every other script) and rewrite
   =bin/statusline.fish= to drop the fish dependency entirely.

Whatever's decided should also cover: should this be written down as
a project convention (e.g. in CLAUDE.md's "Repository layout" or a new
"Scripting conventions" note) so it doesn't have to be
re-litigated per script.
